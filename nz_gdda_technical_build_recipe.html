How to build it — Toloa Fund on Salesforce PSS

Concrete Salesforce architecture and delivery approach for the grants lifecycle specified at Level 4. Foundation stack, data model, applicant experience, business logic, integration and events, AI, packaging, security, team, and first sprint. The technical companion to the L4 process drill-down.

01Foundation — the Salesforce Public Sector Solutions stack

Salesforce PSS is a bundle, not a single product. The grants lifecycle uses the core CRM plus a specific set of add-on capabilities. All of the following are pre-integrated in a PSS org and provisioned at licensing time.

Core platform

  • Sales & Service Cloud — base CRM: Account, Contact, Case, Task, Queue, Approval
  • Public Sector Solutions data model — Individual, Party Relationship Group, License, Benefit
  • Salesforce Grants Management — FundingProgram, FundingOpportunity, FundingRequest, FundingAward, Disbursement, Requirement
  • Experience Cloud — applicant portal (LWR-based)

Low-code & logic

  • OmniStudio — OmniScript, FlexCard, DataRaptor, Integration Procedure
  • Business Rules Engine (BRE) — eligibility, decisioning, scoring
  • Flow & Flow Orchestration — screen flows, record-triggered flows, multi-user orchestrations
  • Approval Processes — delegation authority, sign-off workflow
  • Lightning Web Components (LWC) — custom UI where needed

Integration, data & AI

  • Platform Events — outbound DPI event publishing
  • Change Data Capture — entity-level sync
  • MuleSoft — integration fabric to DPI Services Exchange
  • Data Cloud — cross-agency harmonised person + outcome view
  • Agentforce — AI agents, Prompt Builder, Einstein Trust Layer
  • Salesforce Shield — encryption, event monitoring, field audit trail

03Applicant experience — Experience Cloud + OmniStudio

The applicant journey — discover, sign in, apply, monitor, close — runs entirely inside an Experience Cloud site. The multi-step application form is an OmniScript. No custom SPA needed.

Portal foundation

Experience Cloud site (LWR)

  • Template: Build Your Own (LWR) — modern, accessible, SPA-fast
  • NZ Government design system as an LWR theme layer (custom LWCs matching design tokens)
  • WCAG 2.2 AA baseline; Salesforce Accessibility Studio validation
  • Multilingual via Translation Workbench + custom translation tables for Pacific languages
  • Login: RealMe federation via OpenID Connect (Auth Provider + Registration Handler apex class)
  • Guest access for public discovery pages (eligibility, program info)

Applicant record type

  • Person Account or Individual (depending on tenant model — Individual preferred for full PSS)
  • Sharing rule: applicant sees own applications only
  • Permission set: Toloa_Applicant — read/write own FundingRequest, upload evidence

Application intake — OmniScript

OmniScript: Toloa_Application_Intake

  • Multi-step: Profile → Family/Aiga → Project → Budget → Evidence → Endorsement → Review → Submit
  • Save-and-resume: DataRaptor Save + Extract per step, backed by FundingRequest record
  • Client-side eligibility rules via BRE Public API (called from OmniScript)
  • Evidence upload: OmniStudio File Upload element → Salesforce Files → virus scan integration → Purview classification via CDC
  • Endorsement: OmniScript branch triggers Endorsement__c creation + email/SMS to matai via Digital Engagement
  • Submission triggers FundingRequest.Status = SUBMITTED and publishes Platform Event

Key LWCs

  • toloaEligibilityCalculator — public-facing pre-check, calls Rules Library via Named Credential
  • toloaAigaRelationshipPicker — custom relationship graph UI for whakapapa/aiga
  • toloaEvidenceUploader — accessible file upload with progress + classification hints

04Assessor & officer experience — Lightning App + Agentforce panel

Staff work in a dedicated Lightning App with an assessment console, workload queue, and embedded Agentforce copilot. Standard Salesforce UI plus a small number of purpose-built LWCs.

Assessor console

Lightning App: Toloa Grants Assessment

  • Home tab: My assigned assessments (Salesforce List View with saved filter)
  • Assessment tab: FundingRequest record page with Assessor layout
  • Related lists: Evidence, Endorsements, Prior Applications, Cross-Agency Awards
  • Utility bar: Agentforce Assist panel (persistent)

Scoring UI

  • Screen Flow: Toloa_Merit_Assessment — one screen per rubric criterion
  • Each criterion score writes to AssessmentScore__c via record-triggered flow
  • Composite score calculated by BRE ruleset Toloa_Merit_Rubric_v1_0
  • Peer-review trigger: record-triggered flow evaluates ambiguity band → assigns second reviewer via Omni-Channel

Workload & routing

Case-style routing via Omni-Channel

  • FundingRequest enabled for Omni-Channel with a service channel
  • Routing configuration: skills-based (STEAM category, Pacific language capability)
  • Queues per assessor pool; presence config controls workload cap
  • Auto-reassignment on assessor absence via scheduled flow

Decision workflow

  • Approval Process: Toloa_Decision_Approval
  • Steps: Assessor recommendation → Program manager review → Delegated authority (if under threshold) → CEO sign-off (if over threshold)
  • Delegation-threshold rule: BRE ruleset Toloa_Delegation_Rules
  • Award letter generation: Docusign or Salesforce Doc Gen from template

05Business logic — Business Rules Engine + Flow Orchestration

Rules are declarative and version-controlled via BRE — not scattered through Apex triggers. End-to-end multi-user process orchestration is Flow Orchestration. This split lets non-developers change rules without releasing code.

Business Rules Engine (BRE)

Rule sets (versioned, published to Rules Library)

  • Toloa_Eligibility_v1_0 — applicant eligibility (age, residency, Pacific descent, prior award history)
  • Toloa_Merit_Rubric_v1_0 — scoring rubric across 5–7 criteria with weights
  • Toloa_Delegation_Rules — decision authority by grant amount
  • Toloa_Compliance_Rules — post-award compliance thresholds
  • Toloa_Milestone_Templates — default milestone schedule

Rule invocation patterns

  • Client-side: OmniScript calls BRE via Integration Procedure (fast, cached)
  • Server-side authoritative: Record-triggered Flow calls BRE on state transition
  • Public DPI: Rules exposed via Named Credential to external DPI Rules Library — same version, single source of truth
  • Rule authoring: Business analyst / program manager in BRE Designer; no code deploy needed to change rule values

Flow Orchestration

Orchestration: Grant_Lifecycle_Toloa

  • Stage 1: Submission → auto-validate (Autolaunched Flow, ~5 sec)
  • Stage 2: Assessor assignment (Omni-Channel routing, human step)
  • Stage 3: Assessment (Screen Flow assigned to assessor, blocking)
  • Stage 4: Peer review (conditional stage, triggered by ambiguity)
  • Stage 5: Decision approval (Approval Process, delegated authority)
  • Stage 6: Disbursement (Autolaunched Flow calling MuleSoft)
  • Stage 7: Milestone monitoring (long-running, scheduled reminders + intake)
  • Stage 8: Closure (Autolaunched Flow, records retention trigger)

Automation surface

  • Record-triggered Flows on FundingRequest state transitions publish Platform Events
  • Scheduled Flows for milestone reminders (30/14/7 day cadence)
  • Event-triggered Flows subscribing to Payment_Confirmed__e etc.
  • All flows source-controlled; deployed via unlocked package

07AI — Agentforce agents, prompts, and Trust Layer

Four Agentforce agents operate across the lifecycle. Each is defined declaratively in Agent Builder with tightly-scoped topics, tool access, and Einstein Trust Layer guardrails. Prompt templates are version-controlled alongside metadata.

Applicant Assist Agent

Scope

  • Guides applicant through form fields
  • Translates fields on demand between English and Pacific languages
  • Explains eligibility rules in plain language (calls BRE)
  • Does not pre-fill fields; does not assess merit

Configuration

  • Topics: ApplicationHelp, LanguageTranslation, EligibilityExplanation
  • Actions: ExplainEligibilityRule, TranslateField, ExplainProgram
  • Trust Layer: PII masking on prompts, retention off, output moderation on

Assessor Copilot Agent

Scope

  • Summarises applicant history + prior applications
  • Cross-references evidence against project narrative
  • Surfaces flagged inconsistencies
  • Does not score; does not decide

Configuration

  • Topics: ApplicantHistorySummary, EvidenceReview, PriorApplicationLookup
  • Actions: QueryPriorApplications, SummariseEvidence, DetectInconsistencies
  • Trust Layer: full PII masking, prompt injection defence, output audit logged

Fraud Signal Agent

Scope

  • Anomaly detection on submitted applications
  • Cross-check against known fraud patterns
  • Publishes signals; never blocks applications autonomously

Configuration

  • Runs on Platform Event Grant_Application_Submitted__e
  • Actions: DetectAnomalyPattern, ScoreFraudRisk, PublishFraudSignal
  • Trust Layer: audit trail full, model provider portability enabled

Compliance Agent

Scope

  • Interprets milestone reports against contract terms
  • Highlights compliance concerns to grant officer
  • Recommends site-visit trigger when thresholds crossed

Configuration

  • Runs on Outcome_Report__c submission
  • Actions: InterpretMilestone, CheckCompliance, RecommendSiteVisit
  • Trust Layer: retention 90 days for audit, feedback loop enabled

08Packaging — the three-layer reference blueprint pattern

Everything above is packaged as three stacked Salesforce Unlocked Packages. The Common Foundation is versioned centrally and pushed to every agency. The NZ Government Overlay adds the shared services connections. The Agency Overlay is where agency-specific configuration lives. Upgrades to the shared layers do not break agency overlays if package boundaries are respected.

Package boundaries are enforced by naming convention (namespace prefix per layer), by permission sets that scope access to metadata layers, and by DevOps Center scratch org validation on every merge. Upgrading Layer 1 or Layer 2 is a one-line command per agency; Layer 3 is deployed via each agency's own pipeline.

09Security, compliance & records

Salesforce Shield + Hyperforce residency + a small set of specific configurations cover the NZ Government controls. Records retention is handed off to M365 Purview via CDC.

Platform security

  • Salesforce Shield Platform Encryption on all PII fields (Individual, Contact Point, evidence documents)
  • Event Monitoring — every login, report export, API call captured; forwarded to security operations via streaming
  • Field Audit Trail — 10-year history on all FundingRequest, FundingAward, decision records
  • Hyperforce residency — AU Sydney region baseline; NZ residency option where available
  • Sovereignty: data at rest in-region; sub-processor list published; foreign-access request policy documented

Access control

  • Permission set groups per persona: Toloa_Applicant, Toloa_Assessor, Toloa_Program_Manager, Toloa_Delegated_Authority
  • Sharing rules: criteria-based sharing so assessors see only their assigned cases
  • Record types: per Toloa program variant (STEAM / Community / Business)
  • Session policies: IP-restricted for staff; standard for applicants
  • MFA: mandatory for all internal users

Records & retention

  • Every FundingRequest CDC event forwarded to M365 Purview via MuleSoft
  • Purview classifies records according to Public Records Act retention schedules
  • Retention actions (destroy / transfer to Archives NZ) triggered by Purview policies
  • Salesforce retains "record of record" pointer to Purview record ID
  • OIA response workflow: Salesforce case with Purview-sourced document links

Privacy & assurance

  • Privacy Act compliance: Data subject request → Salesforce case → Flow orchestrates export, correction, or deletion across systems
  • Data minimisation: only fields tagged in the canonical schema are collected; extensions require justification
  • Consent management: Individual.ConsentEvent records track what an applicant has agreed to share
  • Audit & assurance: annual conformance re-check against EDA patterns (part of certification recertification)

What this shows

Every capability described above is either a native PSS product (Grants Management, OmniStudio, Business Rules Engine, Flow Orchestration, Experience Cloud, Agentforce) or a standard Salesforce mechanism (Platform Events, CDC, Unlocked Packages, Shield). Roughly 85% of the build is configuration; the remainder is custom LWCs, MuleSoft flows, and agency-specific overlays. The technical risk lives in the integrations, not the platform.

The three-layer package structure is what makes the certification framework technically real. Layer 1 is versioned centrally; Layer 3 is owned by the agency; upgrades to shared layers do not break agency configuration provided the boundaries are respected. This is the same pattern Service Victoria explored with its base package concept, applied at NZ Government scale.

For a first-cohort agency of ~100 FTE with a defined program like Toloa, a full end-to-end greenfield build on this stack is a ~6-month delivery with the team above. Ministry for Women following on with Nominations Service (reusing Layers 1 & 2, replacing Layer 3) is ~2 months. Whaikaha with provider oversight is ~3 months. That reuse arithmetic is what turns the Cabinet cost story into something measurable.
