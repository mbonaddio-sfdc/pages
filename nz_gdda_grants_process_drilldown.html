Grants lifecycle — Level 4 drill-down

The full end-to-end grants process — Toloa Fund as the concrete instantiation — specified at Level 4. Every sub-process, every persona, every data entity, every rule, every integration event. This is what the "common process" for grants looks like when it's codified as configuration on the certified reference blueprint, not documented as policy.

Version 0.1 · working reference · Salesforce Public Sector Solutions Grants blueprint · Toloa Fund overlay

The argument this artefact makes

GDA's current common-process work is oriented toward documenting each process to 8 levels of policy detail. That work is important — but it doesn't produce a running system. The alternative below is the same process, but specified as configuration on a certified reference blueprint: 58 Level-4 sub-processes, each with an owner, a persona, a platform component, a data entity, a rule, and an event. Every element of this specification is executable. Deploy it once, agencies adopt it with their own eligibility criteria, scoring rubrics, and program metadata layered on top. The common process is the reference blueprint.

What this shows — common process, codified as configuration

Everything above is one grants process, specified at Level 4, with every sub-process assigned to a persona, a certified platform component, a data entity, a rule, and a published event. Fifty-eight sub-processes. Eight phases. Fifteen data entities. Twenty-four rules. Seventeen DPI events. Nine personas. All of it configured on the Salesforce Public Sector Solutions Grants blueprint — the certified Reference platform for Citizen Service Delivery — with the Toloa Fund overlay providing MPP's program-specific eligibility, merit rubric, and milestone template.

This is what the "common process for grants" actually is when it's built rather than documented. Not eight levels of nested policy — one Level 4 specification, expressed as configuration, running on a shared platform with events published to DPI. Ministry for Women reuses 90% of this same specification, changing the eligibility rules, the merit rubric, and the milestone template. Whaikaha reuses ~70%, replacing the merit-scoring lane with an oversight-monitoring lane. That's what reuse actually looks like.

The cost story. Building this once at the certification body level and letting agencies overlay their program-specific rules replaces an 18–24 month per-agency build. For three small ministries, that's three fewer separate grants system builds and one shared upgrade path. Multiply that across the ten agencies Mel identified and the arithmetic against Driving Down the Cost of Digital starts to look real.

What we would take to Andy. This artefact is the answer to the question “what does common process actually mean and how deep does it need to go?” The answer is: as deep as this — no deeper. Any further depth is deployment configuration, not common process definition. The common process is the blueprint. The blueprint is the specification. Adopt it, layer your program-specific rules on top, and deliver in months instead of years.
