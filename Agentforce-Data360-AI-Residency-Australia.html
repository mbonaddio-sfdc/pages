The #1 concept for AEs

04Prompts vs Agents — why masking differs

Data masking behaves differently depending on the path. Getting this right is the single most important thing when a customer asks "is my PII masked?"

Prompt path · single-shot

Masking ON

Prompt Templates, Flow, embedded GenAI (Service Replies, Work Summaries, Draft Emails, Search Answers), Models API. PII is replaced with deterministic tokens (e.g. <Person_0>) before leaving SF, then unmasked on the response.

Agent path · multi-step planner

Masking OFF

The Atlas Reasoning Engine plans, acts, observes and re-plans over many steps. The output of one step becomes the input to the next, so the planner must reason over the real values — not placeholder tokens — to know which record it's acting on and to feed correct arguments into each action.

Why a masked token breaks the agent loop

Imagine the agent handling "Jane Citizen, jane@example.com". If masking replaced her name with <Person_0>, the planner would then have to:

  • Look up her cases — but a query needs the real identifier; <Person_0> matches no record, so the search returns nothing.
  • Check eligibility & call the next action — each action must be passed real arguments (a record ID, an email to send to); a token can't be executed against.
  • Re-plan on what it observed — the planner reasons over the actual results to decide the next step. Masked values give it nothing concrete to reason about, so the chain collapses.

A single-shot prompt never has this problem because it does one pass with no follow-on action — so its PII can safely be tokenised and unmasked on return. The agent's plan→act→observe loop cannot.

Say this out loud

"Masking off for agents is a permanent architectural decision, not a gap on the roadmap. It's how the planner works — and the controls that protect you instead are coming up in slide 06."

The lifecycle

05How a request flows end-to-end

Before the controls, the mental model: one request can take two very different routes. The planner service decides which, and that choice is what drives masking, residency and access behaviour downstream.

1 · Request

User asks

A person (or a system event) invokes an AI capability — a chat message, a "summarise" click, a triggered flow.

→
2 · Planner service

Atlas Reasoning Engine

Interprets intent and decides the route: a single-shot prompt, or a multi-step plan that calls agent actions.

→
3 · Execution

Prompt or agent actions

Either one grounded prompt call, or a loop of actions (Flow, Apex, prompts) reasoning over real record values.

→
4 · Response

Return & log

Result is returned to the user; the full generation is written to the audit trail in Data 360.

Route A · Prompt path

Single-shot template

The planner (or a direct feature call) issues one grounded prompt — a summary, a service reply, a draft email. It does one pass and returns. Because there's no follow-on action, PII can be masked going out and unmasked on return.

Route B · Agent path

Planner + agent actions

The planner runs a plan → act → observe → re-plan loop, invoking agent actions with real record values so each step can build on the last. This is powerful but is why masking is off and access control becomes the primary safeguard (next slide).

The through-line

The planner service is the fork in the road. Which route it picks determines everything downstream — whether data is masked, whether the loop needs real values, and which controls actually protect you. The prompt-vs-agent slide before this and the controls slide after it are the two sides of that fork.

Under the covers

06The planner & controls for data access

The Atlas Reasoning Engine drives the agent loop. Because masking is off on this path, access control — not masking — is the primary protection.

Plan

Interpret the goal, select topics & actions.

→
Act

Invoke an action (Flow, Apex or a prompt) with real values.

→
Observe

Read the result of the action.

→
Re-plan

Decide the next step or finish.

Primary control = Field-Level Security plus least privilege

Agents run in the running-user context — never as the system. If a field is hidden from that user by Field-Level Security, it can never reach a prompt. Combine this with the principle of least privilege on the agent user, so the agent only ever sees what that persona is allowed to see.

  • Field-Level Security and hidden fields — the hard boundary; enforced regardless of how the prompt is worded.
  • Explicit merge-field selection — only bind the specific fields the action actually needs.
  • Topic scope — "must / never / always" instructions that constrain what the agent will do.
  • Principle of least privilege on the agent user — the running-user's permissions cap how much data any action can reach.
  • Business rules in code — put deterministic logic in Flow or Apex, not in natural-language model instructions.
  • "Available When" conditions — gate each action so it only runs in valid states.

The toggle — current name & scope

The control is now called "Enable In-Region Model Requests Only" (Setup → Einstein Setup). It's the effective kill switch for cross-region traffic. It is set per-org, not globally — a global preference has been proposed but not built. It currently covers Azure OpenAI and AWS Bedrock (including Anthropic).

As of Aug 2026: ~4,115 orgs have enabled in-region-only, unblocking 700+ strict-residency orgs.
Fail-safe over failover

08When fallback is disabled — what happens

Turning on "In-Region Model Requests Only" trades availability for residency. Set the customer's expectation before they flip it.

The trade-off

Residency is prioritised over uptime

With the toggle on, the platform will not route offshore to keep the request alive. If the AU model endpoint is unavailable, the request fails rather than leaving the region.

The experience

The request returns an error

Instead of a silent US fallback, the caller gets an explicit failure — the model call does not complete. Design agents/prompts to handle that gracefully (retry, degrade, or inform the user).

How to position it

"You choose the posture. Leave fallback on for maximum availability with a small chance of transient US processing during an AU outage, or turn on in-region-only so nothing ever leaves AU — accepting that a rare AU outage means the AI feature is unavailable rather than served from the US."

Scope reminder

The toggle is org-level. There is no separate hard-block or account-wide switch today — this toggle is the kill switch, applied per org.

Observability

10Audit trail — what's captured & where

The Trust Layer logs every generation to the customer's own Data 360 — not a central Salesforce store.

Fields captured
  • The prompt and the response.
  • Toxicity / safety scores and detector output.
  • Feedback signals (thumbs up/down).
  • Timestamps & identity (who invoked it).
  • LLM parameters (model, settings).
Where it lives

Stored in the customer's own Data 360 in-region (Sydney), across DMOs such as GenAIGatewayRequest/Response, GenAIGeneration, and GenAIAppGeneration.

Because it's their Data 360, the customer owns access control and retention — which is the whole point of the next slide.

Session Tracing complements this: reasoning executions, action calls, gateway I/O and errors.
Govern the logs themselves

11Audit trail — PII, access & retention

Because masking is off on the agent path, the audit log can contain unmasked PII. The log becomes sensitive data you must govern like any other.

The key caveat

For the agent path, prompts/responses in the log are unmasked. Apply FLS on the DLOs, Data 360 access policies, and retention governance to the logs — don't treat audit data as low-sensitivity.

Access

Role-scoped in Data 360

Data Cloud Architect = full; Data Cloud User = view-only. Data spaces and policies restrict further. Grant on need-to-know.

Retention

Default 30 days

Auto-retention configurable to 30/60/90 days; purge ~24h after expiry. "Permanent until deleted" is the Shield-extended option — not the default.

Talk track

"The audit trail is a feature and a responsibility. It gives you full observability of every AI generation — in your own region, in your own Data 360 — but because agent logs can hold real PII, you govern it with the same FLS and retention discipline as any customer data."

Zero Data Retention (ZDR)

Contractually enforced across OpenAI, Azure OpenAI, Anthropic-on-Bedrock and Google. Attested via SOC 2 Control PR-19, validated quarterly.

Nuance: providers still run automated safety-scanning classifiers — so it's "no retention", not "no processing". Anchor to Einstein Platform NLI, not a raw provider contract.

What we can't contractually commit

Per Public Sector Legal, Salesforce cannot contractually commit to Agentforce data residency — in-region processing is a technical default, not a contract term. Set expectations accordingly.

Encryption: AES-256 at rest, TLS 1.2+/mTLS in transit; CMK/EKM/BYOK, BYOK available in the Sydney zone. Also relevant: APP, APRA CPS 234, NSW AIAF (genAI = elevated risk).
Things to be aware of

13Considerations & caveats

The edges that trip reps up — pre-empt these before the customer does.

Agentforce Coworker

Auto-enabled at GA (4 Aug 2026). Runs on the agent path (masking off) and has an open US-fallback gap during outages. The disable toggle has no confirmed ship date — flag this for strict-residency customers.

Controller / processor

Customer = controller, Salesforce = processor. Residency configuration is customer-owned — which is why "who's responsible for turning fallback off?" is answered: the customer.

Common misconceptions to pre-empt
  • "Core CRM residency = AI residency." No — each AI capability routes independently.
  • "Masking is always on." No — off for the agent path by design.
  • "ZDR means onshore." No — ZDR is about retention, not location.
  • "Slack AI stays in my region." No — Slack AI is US always.
  • "Tableau Next is all AU." No — Stage 2 Native Services are US-only.
Takeaway

14What to carry into every conversation

AU residency is a configuration outcome — not a default. Your job is to know the map and set expectations honestly.

  • Know where each product processes — the matrix is your cheat sheet; Slack & Tableau Next Stage 2 are the traps.
  • Mask where you can, control access where you can't — prompts mask; agents rely on FLS + least privilege.
  • Govern the logs — audit data can hold unmasked PII; apply FLS, policies and 30-day retention.
  • Disable fallback where residency is required — "Enable In-Region Model Requests Only", per org, accepting the availability trade-off.
  • Don't over-commit — residency is a technical default, not a contractual guarantee.
